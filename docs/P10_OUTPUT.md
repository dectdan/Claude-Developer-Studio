## Decisions I made

1. **One store-wide zip, not per project** (as the prompt asks), named `ClaudeDevStudio-store-<yyyyMMdd-HHmmss>-<kind>.zip`: the prompt's name plus the **kind** (`daily`, `upgrade`, `manual`, `pre-restore`, `pre-import`) as a suffix, so the keep rule never has to open a zip and a manual backup can never be mistaken for an automatic one.
2. **Keep rule:** newest 14 `daily`, newest 4 `upgrade`; `manual`, `pre-restore`, `pre-import` and exports are **never** deleted (they belong to something the user did; a pre-restore backup may be the only copy of what a restore overwrote).
3. **`chat_mirror.jsonl` is included.** It is what `claudedev_chat_resume` reads (a dropped chat's checkpoints), 261 KB on Dan's PC; losing it with the disk would lose that. It stays out of search (unchanged). Also excluded, besides `Backups\`: `VSBridge\` (Visual Studio's live state, 1.6 MB, rewritten while VS runs), `hook_state\` (once-per-file markers), `.cds-memory\` (the old git sync's copies), `*.tmp`, `*.lock`.
4. **When the daily backup runs: both the CLI's `load` and the tray app.** `load` is what every user has (Claude Desktop and the Claude Code hook both call it), so it checks "is there a daily backup with today's date" (one directory listing) *after* writing its output and, if not, starts `claudedev backup --auto` on its own through ShellExecute and returns: measured 236–239 ms for the whole load through Node's `execFile`, and the backup survives the hook's Node exiting at once. The tray app (if it runs) does the same check 2 min after start and every hour, so a day without a load still gets one when the PC is on. "Today" = the local calendar date; a lock file stops two at once.
5. **`AutoBackupScheduler.cs` deleted** (`git rm`): it was never instantiated, worked per project, and its triggers (every 50 activities, before a handoff) would have run inside a hook's 1.5–15 s budget. `claudedev backup <project>` (the per-project `.backup` zips) is kept and fixed (item 4 of section 1).
6. **The pre-upgrade backup runs with the new CLI right after it is copied**, before anything else in the installer runs (`backup --upgrade`, only when a version was registered or a CLI was installed). The old CLI can't do it (no `--all` before 1.7), and the files the installer copies are programs, not memory, so "right after the CLI is copied" protects the memory exactly as "before" would. It never fails the install; its output goes to `install.log` ("Memory backup (exit 0): …").
7. **Import vs restore:** import **merges** (never removes, never duplicates), restore **replaces** (writes every file of the backup back) but **never deletes** files that aren't in the backup. Both back up first (`pre-import`, `pre-restore`). Both verify every hash before writing anything and refuse a damaged or foreign zip. Restore asks unless `--yes` (an MCP or script caller gets "cancelled", since it reads an empty answer).
8. **What counts as the same entry:** an identical line, or the same timestamp (to the second) and the same main text field (`mistake`, `decision`, `description`, `pattern`, `lesson`, `where_i_stopped`, `operation`, `content`, `message`). A new entry whose ID (`ERR005`) is already used by a *different* entry gets the next free ID and keeps the old as `original_id`, so IDs stay unique (P1's rule). Entries are appended, so existing lines never move.
9. **Files that differ and aren't JSON lines** (FACTS.md, notes, ground-truth copies): the newer one (file time from the manifest) stays and the other goes to `Backups\import-kept\<time>\`; nothing lost either way. This PC's own state (`session_state.json`, `file_digests.json`, `cli_session_state.json`, `phases.json`, the `.bak` files) is kept.
10. **Conflict copies are merged by the CLI on `load`, `record` and `lesson`**, before they read or write (so a new ID is numbered after the copy's entries too); `cds-context.js` and `cds-search.js` *read* a copy that is still there (an older CLI, or a copy that appeared after the last load) and drop duplicates, but never write: search is read-only by design (§4), and the CLI owns every write (§6). `FACTS-PC.md`, `UNCERTAINTIES-PC.md`, `session_state-PC.json`, `file_digests-PC.json` are only moved aside (the main file kept; no entries to merge). The PC name in the report is the file name's suffix as written.
11. **`git`, `cloud`, `sync` removed** (section 5): they print one line (removed in 1.7.0, why, use export/import, `backup --status`) and exit 1, like `monitor` in 1.5.0; nothing they made is deleted.
12. **The smoke test is isolated with `--cli`** (whole run on throwaway roots), because this phase's rule makes Dan's store read-only and P9's suite made (and removed) a throwaway project folder in it; the installed copy is tested the same way with `--cli <installed CLI>`.
13. **`SessionStateManager.GetMemoryPath` no longer creates the folder** and follows `MemoryPaths.Root` (it created an empty folder in Dan's store during this phase's first test: section 9).
14. **Default export location:** beside the store, `[Documents]\ClaudeDevStudio-export-<time>.zip` (not inside it: an export inside the store would be in the next backup). The tray app's dialog starts in Documents.
15. **I wrote nothing more to Dan's real memory store** after the one mistake recorded early on (the prompt makes the store read-only for this phase): no activity/decision/handoff records through the CDS tools. ## Facts used, with sources

- **OneDrive's conflict copy name.** Microsoft: "If a conflict occurred with a non-Office file type, OneDrive automatically keeps both versions. The online version keeps the original file name and is downloaded, and the copy on your computer has your device name appended to the file name such as Report-JOHNS-SURFACE.txt." and "OneDrive for work or school creates up to 5 conflict versions for non-Office file types." ([Resolve sync issues in OneDrive for work or school](https://learn.microsoft.com/en-us/troubleshoot/sharepoint/sync/troubleshoot-sync-issues)). Same `name-COMPUTERNAME.ext` example in a university KB ([UWindsor: Known Issue: OneDrive duplicate files](https://uwindsor.teamdynamix.com/TDClient/1975/Portal/KB/Article/29832/Known-Issue-OneDrive-duplicate-files)) and `Report-DESKTOP-ABC123.docx` in vendor guides ([wisechecker](https://wisechecker.com/?p=29862)). I found **no official statement of the numbering** of further copies (a Q&A user reports `-1`, `-2` suffixes: [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/4933245/file-duplicates-are-created-in-sharepoint?page=2)); the pattern therefore takes any `-<letters, digits, hyphens>` suffix (PC names contain hyphens, e.g. `DESKTOP-OPUU7C8`), which covers a numbered one too. Dan's store has no conflict copies today (read-only scan).
- **Is a folder inside OneDrive?** OneDrive records each account under `HKCU\Software\Microsoft\OneDrive\Accounts\<Personal|Business1…>` with a `UserFolder` value (Microsoft's archived deployment guide lists `Accounts\Business1\UserFolder` and `Accounts\Personal` in OneDrive's own registry reads: [OneDrive Next Generation Sync Client Deployment guide](https://learn.microsoft.com/en-us/archive/technet-wiki/33549.onedrive-next-generation-sync-client-deployment-guide)); the `%OneDrive%`, `%OneDriveConsumer%` (personal) and `%OneDriveCommercial%` (work/school) variables point at the same folders ([University of Waterloo IT](https://uwaterloo.atlassian.net/wiki/x/doRPHgo); a [forum thread](https://forum.multicommander.com/forum/index.php/topic,3860.0.html) warns the variables and the registry can disagree, so CDS reads both). Known Folder Move values such as `KfmFoldersProtectedNow` exist under the account key ([Microsoft Tech Community](https://techcommunity.microsoft.com/discussions/onedriveforbusiness/what-do-the-kfm-values-under-hkcu-onedrive-do/2992371)) but have no documented meaning, so CDS doesn't rely on them; it compares the memory root's real path (after Windows' Documents redirection) with the account folders instead. Checked on Dan's PC, read only: `Accounts\Personal\UserFolder` = `C:\Users\<user>\OneDrive`, `%OneDrive%` the same, Documents = `…\OneDrive\Documents`, `KfmFoldersProtectedNow` = 3584.
- **Is OneDrive running?** A `OneDrive.exe` process in the current Windows session (Dan's: `C:\Program Files\Microsoft OneDrive\OneDrive.exe`). No API, no sign-in.
- **Cloudflare R2** authenticates its S3 API with AWS Signature Version 4 and an access key ID + secret ([R2: S3 get started](https://developers.cloudflare.com/r2/get-started/s3/), [Presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)); `CloudSyncManager` sent `Authorization: Bearer <token>` to `https://<account>.r2.cloudflarestorage.com/<bucket>/<file>`, which can't authenticate.
