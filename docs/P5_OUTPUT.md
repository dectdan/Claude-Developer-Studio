## Decisions I made

1. **Search's words are the mistake rule's words, plus two additions for recall.** Same tokens as `keywords()`/`MistakeMatching` (4+ characters of `[a-z0-9_.-]`, lower case, the same stop words). Added: the 4+-letter parts of tokens joined by `.`, `_` or `-` (so "config" finds `cds-config.js`, and "path." at a sentence end is "path"), and a query word matches the same word with an inflection (`s es ed d er ers ing ings`, either way: "quotes"/"quote", "installer"/"install"; not "curly"/"curl", which a 3-letter tolerance had matched in the first try, a GainPottery `curl` line).
2. **How many words must match:** all of them for one or two words; otherwise at least half and at least 2 ("OneDrive Documents path": 2 of 3). Quoted phrases are supported (cheap): each must appear in the entry as written, spaces collapsed, any case.
3. **Ranking:** more matched words first; then kind (lessons, mistakes, decisions 5; patterns, handoffs 3; activity 1; the hook's `file_edit` lines 0); then **BM25** (rarer words in shorter, denser entries first); then newer. BM25 is an addition to the prompt's order: without it, ties went to the newest entry, and long session summaries that mention every word buried the precise entries. Example from the real store: for "OneDrive Documents path" the ClaudeDevStudio v1.2.1 fix ("VS Bridge MCP server path resolution for OneDrive-redirected Documents folders") was not in the first 15 lines by date; with BM25 it is third, after two mistakes.
4. **Activity can't crowd out the rest:** activity gets at most a third of the lines (5 of 15) while other kinds still have hits to show; only when there are fewer of those does it fill the free lines. Tested: 12 mistakes and 40 newer activity lines with the same words give 10 mistakes and 5 activity lines.
5. **Output:** a first line (query, hits, projects, how many shown by kind, the words and how many must match), a `Files:` line naming the store roots once, then one line per hit: `- <date> <kind> <project>\<file> <id>: <text>`; a mistake shows `| lesson:`, a decision `| why:`, a handoff `| next:`. When the first matched word is past the visible width, the line shows the start, `...`, and the text around the word. Lines shrink from 220 to 80 characters of text, then drop, to fit **3,000** characters (with `limit` up to 40, up to 6,000; never more). Old-store files are marked `old:`.
6. **The lessons are searched too** (kind `lessons`), also in a one-project search: they apply to every project.
7. **No index.** The whole store is 2,963 small files; one at a time the reads take 1.5 s, because each open costs ~0.4 ms here (a `stat` costs 0.015 ms; Windows Defender's real-time scanning is on, the likely cause: inference, not measured). 32 reads at a time: ~240 ms. Search lists the folders, reads concurrently, tests each raw line for the words' stems before parsing it, and takes 300–390 ms in the server for the full store. An index would be a second copy of the memory to keep in step; not worth it at this size.
8. **Search writes nothing, not even the chat mirror.** Every tool call appends a line to `chat_mirror.jsonl` at the store root; search skips it, so "read-only" holds for the whole store (the smoke test compares the throwaway root before and after, and caught exactly this).
9. **The lessons file:** `LESSONS.jsonl` at the memory root, one JSON object per line: `id` (`LSN###`), `timestamp`, `lesson`, `why` (where it was learned: project, date, what happened), `source_project` (optional), `updated` (after an edit). Written only by the CLI.
10. **The CLI command:** `claudedev lesson add <json> [--force]`, `lesson add --file <f.jsonl> [--force]` (one per line, for seeding), `lesson list`, `lesson edit <LSN###> <json>` (given fields replace, others kept), `lesson remove <LSN###>`. Edit and remove rewrite the file through a temp file after copying it to `LESSONS.jsonl.bak`; a removed lesson's number isn't reused while the backup holds it. `--force` is CLI-only (the producer's escape hatch for a wrong refusal); the MCP tool never forces.
11. **Near-duplicate threshold:** the mistake rule itself (at least 3 shared words making at least 30% of the smaller word set), on the two lessons' texts only (not `why`, which names projects and dates). It is strict for short lessons: candidate 10 was first refused as a duplicate of candidate 4 (shared: exists, copy, packaged, editing) and was reworded.
12. **Lessons in `load`:** right after "Mistakes to avoid" (the project's own mistakes first, then the machine-wide ones, before decisions: lessons are mistakes to avoid too). Trim order: activity, patterns, uncertainties, facts, decisions, **lessons**, output, questions, mistakes (lessons go before the project's own output and mistakes, after the rest). Three variants: up to 1,200 characters, up to 600, one line. **Order: the most relevant first**, the most of a lesson's words found in the project's ground truth and mistakes, then the newest; without either, newest first. (With all lessons seeded at once, "newest" is just the reverse file order; SongSpark then led with WinUI packaging lessons. Ranked, it leads with the Bash/backslash lesson it has recorded itself.) **No lessons file, or an empty one: no section at all** (my choice: zero characters for every user who never records a lesson).
13. **`check_mistake` and lessons:** the lesson's text only, the same rule. The MCP tool runs the CLI's check (which now also checks lessons; exit 1 for either kind of match) and its own Node check (which also covers the old store and works with an older CLI); it prints its own results and shows the CLI's text only when the CLI found something it didn't (before, both were printed, saying the same thing twice).
14. **`record_mistake`'s suggestion:** the new mistake (mistake + lesson) against every other project's mistakes in both stores, same rule, best match per project; two or more other projects → one paragraph naming them and suggesting `claudedev_record_lesson` ("a suggestion: nothing else was written"). If a lesson already matches it, the reply says which instead. A failure here never fails the record.
15. **Test-only overrides:** `CDS_MEMORY_ROOT` (the CLI, `cds-paths.js`, the hook) and `CDS_LEGACY_ROOT` (the servers). The P5 smoke checks run a second server against a throwaway root and old store in `%TEMP%`, so no lessons test can touch the real `LESSONS.jsonl` (checked at the end: its size and time unchanged, no throwaway name in the real store). The lessons checks need `--cli`: an older CLI ignores `CDS_MEMORY_ROOT` and would write to the real store, so they are skipped without it. `MemoryPaths` is in `ClaudeMemory.cs` (the tray app and the Dashboard compile that file, so they follow the variable too; it is never set in normal use).
16. **The keyword rule moved** from `index.js` to `cds-context.js` (`STOP`, `keywords`; load's ranking uses them) and `cds-search.js` (the thresholds, `similarMistakes`, `similarLessons`), unchanged; it still mirrors `MemorySchemas.cs`.
17. **`show.mjs` passes `CDS_*` variables to the server.** The MCP SDK hands a spawned server only a short whitelist of environment variables; my first "load with lessons" measurement silently read the real store because of that. Also new: `show.mjs claudedev_search "<query>" [project|-] [kinds|-] [limit]` and `show.mjs --tools`.
18. **Item 5, the second location:** see below; the rule is in `cds-config.js`'s header.
19. **Uninstall on a PC that never had Claude Desktop** removes `%APPDATA%\Claude` only when everything in it is CDS's: the config file and `claude_desktop_config.json.bak-cds-*` backups, each holding nothing but CDS's two entries. Any other file (Claude Desktop's own) and the folder stays, with only CDS's entries removed.
20. **`claudedev configure-claude` without Claude Desktop** (the tray app's "Link Claude Desktop") now does what the installer does (writes the entries, says to install Claude Desktop, sign in, quit and reopen once) and exits 0, instead of "Claude Desktop not found" and exit 1. No tray app change was needed: it shows the CLI's text.
21. **The installer logs its finish-page text** (`[setup] Finish page: ...` in `install.log`), so silent installs and the sandbox can check what a user would read.
22. **Not fixed, reported:** `SessionStateManager.cs` (the CLI's `switch`/`active` project state) writes `%APPDATA%\ClaudeDevStudio\session_state.json`. When the CLI runs under the packaged Claude Desktop, that write is virtualized into Claude's package folder (Dan's PC has `...\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\ClaudeDevStudio\session_state.json`, 2026-11-10). ## 5. A PC that has never had Claude Desktop

**Where Claude Desktop for Windows reads its config (sources, read 2026-11-11):**
- **The installer from claude.ai/download installs an MSIX package.** `https://claude.com/download` (claude.ai/download redirects there) links `https://claude.ai/api/desktop/win32/x64/setup/latest/redirect` and the Microsoft Store (`apps.microsoft.com/detail/9P6K58THS811`) and says the app "supports standard enterprise deployment with MSIX installers (Windows)". Anthropic's "Deploy Claude Desktop for Windows" (`support.claude.com/en/articles/12622703`, "updated over a week ago") gives the MSIX at `https://claude.ai/api/desktop/win32/x64/msix/latest/redirect`, "packaged as a per-user application", `Add-AppxPackage`. It does not say where the config is. On Dan's PC: package `Claude_pzs8sxrjxfjjc` 5.1231.2.0, signature kind Developer (sideloaded, not the Store), and its manifest keeps file-system write virtualization **on** (only `%LOCALAPPDATA%\Claude-3p`, `Claude-Data`, `Claude\logs` and an Office folder excluded). It also carries a non-virtualized helper, `claude-make-data-folder.exe` (`uap10:RuntimeBehavior="win32App"`), presumably to create the data folder outside the package (inference from its name).
- **Microsoft (MSIX, "Understanding how packaged desktop apps run on Windows", `learn.microsoft.com/windows/msix/desktop/desktop-to-uwp-behind-the-scenes`, ms.date 2026-09-30):** for a virtualized app on Windows 10 1903+, "all newly created files and folders in the user's AppData folder ... are written to a private per-user, per-app location", "modifications to existing files under the user's AppData folder is allowed", and on opening a file "the OS will open the file from the per-user, per-package location first. If that location doesn't exist, then the OS will attempt to open the file from the real AppData location", "no virtualization for that file occurs". The private location is `%LOCALAPPDATA%\Packages\<package family>\LocalCache\Roaming\...`.
- **Users (github.com/anthropics/claude-code/issues/26073, opened 2026-02-16, still open 2026-11-10, Claude Desktop 1.1.3189.0 MSIX):** a fresh MSIX install reads `%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\claude_desktop_config.json` while Settings › Developer › Edit Config opens `%APPDATA%\Claude\claude_desktop_config.json`, so servers written to the latter are ignored without a word; installs where `%APPDATA%\Claude` already existed (an earlier non-MSIX Claude, or the folder created by hand before installing) use the real folder.
