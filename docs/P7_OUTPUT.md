## Decisions I made

1. **Names:** `claudedev_phase_start/status/reply/stop`, like the workbench's other `claudedev_vs_*` tools.
2. **One module, two roles:** `mcp-server\cds-phase.js` holds the tools' logic and the runner (`node cds-phase.js --run <json> <n>`), so nothing else ships.
3. **Started through WMI, not as a child of the server.** Claude Desktop ends its servers when it quits; a detached Node child may still sit in a job object that a host closes. `Win32_Process.Create` makes WMI the parent (seen: `WmiPrvSE`), hidden (`ShowWindow 0`). If WMI fails, a detached child is started instead and the reply says so.
4. **The run gets the user's own environment** (what WMI builds from the profile, checked: the full user `Path`, `ComSpec`, `PATHEXT`...), not the server's. Claude Desktop may give its servers a reduced environment, and a parent Claude Code session's `CLAUDECODE`/`CLAUDE_PROJECT_DIR` must not reach a phase (P4's rule that bites). Smoke checks that a server started with `CLAUDECODE=1`, `CLAUDE_PROJECT_DIR` and a test variable passes none of them on.
5. **A reply's message goes in on stdin**, from a `%TEMP%` file removed when the run ends; never as an argument. `claude -p "<text>"` takes the prompt positionally, so a message starting with `--` (say `--dangerously-skip-permissions`) would otherwise be parsed as a flag. The producer's facts had `< NUL` and the prompt as an argument; the start still does exactly that (fixed text from a validated phase name). Verified with real Claude Code (T1's reply).
6. **Replies are appended to the same log;** the `.json` records each run's byte offset, so Status reports the current run ("run 2 of 2, a reply") and `phase-status.ps1` still shows the newest result.
7. **Starting a phase that already has a finished run** moves its old `_run.log/.err/.json` to `docs\phase_runs\<phase>_<yyyymmdd_hhmmss>_run.*` rather than overwriting or refusing (nothing lost; this repo's `.gitignore` now covers `docs/phase_runs/` and `docs/cds_phase.lock`).
8. **Minimum Claude Code 2.1.0.** The ground truth records 2.0.42 lacking `--effort` and 2.1.x having it; I didn't find the exact first version with `--effort`, so the floor is the first 2.1 release. No newer flag is used (`--permission-prompts`, which needs 2.1.259, is not passed).
9. **Flags kept as `run-phase.ps1` had them.** Not added: `--bare` (it would skip the user's hooks, CLAUDE.md and their subscription login: the docs say bare mode needs `ANTHROPIC_API_KEY`), `--strict-mcp-config`, `--session-id`, `--permission-prompts none`, `--max-turns`. A phase therefore runs with the user's own Claude Code settings and hooks, as any of their sessions.
10. **Default allowed tools:** `run-phase.ps1`'s twelve built-in names plus all 13 memory tools by their current names (including `claudedev_record_lesson`, which writes the machine-wide lessons file; the prompt said "the 13"). **No workbench tools:** the run's MCP config has only the memory server (as `run-phase.ps1`'s), and a phase must not start, answer or stop phases. `allowed_tools` given by the caller is checked: each entry must look like a tool or rule (`Read`, `Bash(git log *)`, `mcp__server__tool`), so `--anything` is refused, and entries naming `claudedev_phase_start/reply/stop` are refused.
11. **`effort`** takes Claude Code's levels without `ultracode` (which turns on multi-agent workflows: too costly to start by accident).
12. **Refusals are tool errors** (`isError`) whose text says why and what to do.
13. **The project rule moved to `cds-paths.js`** (unchanged code, exported) so the hook and the phase tools share one copy; `cds-paths.js` wasn't in the prompt's list, but it is an already-shipped shared module and the alternative was a second copy of the rule.
14. **`tools\phase\*.ps1` stay as they were**, with a header saying the tools replace them and how the two interoperate.
15. **Stop is `taskkill /PID <runner> /T /F`,** after checking the pid is still the runner (start time within 60 s of the record, `cds-phase.js` in its command line; for a `run-phase.ps1` run, its `cmd.exe` with `claude` in it). No gentle stop: see §7 item 24.
16. **Status lists CDS's two MCP servers by name and counts the rest** (Dan's runs see 44 servers; listing them blew the budget).
17. **The sandbox kit** (`tools\sandbox-test\in-sandbox.ps1`, not in the prompt's list but the installer's test): `Check-Program` lists `mcp-server\cds-phase.js`, and the workbench check expects 17 tools including the four phase tools (it said 13).

## Facts used from Claude Code's docs

- **Headless mode, exit codes, results** (https://code.claude.com/docs/en/headless): `-p` runs non-interactively; "exits with code 0 on success and a non-zero code when the run fails"; with `stream-json` "the last line of the stream is a `result` message with the final response text, cost, and session metadata"; `system/init` "reports session metadata including the model, tools, MCP servers" and is first unless SessionStart hook events precede it (seen: `hook_started`/`hook_response` first); denials "appear as `permission_denied` system messages, and the final result message lists them in `permission_denials`"; `--resume` with a session ID continues a specific conversation and finds it "in any project on this machine"; a run "can stay open to wait for background work" (seen in T2); SIGTERM gives exit 143 and runs SessionEnd hooks (not available on Windows for another process: §7 item 24); with v2.1.302+ a `-p` run without a mode starts in Manual mode, so the mode must be set (it is: `acceptEdits`); `acceptEdits` "writes files without prompting" and auto-approves common filesystem commands, other shell commands and network requests need an `--allowedTools` entry; `--bare` skips hooks, MCP servers and CLAUDE.md and needs `ANTHROPIC_API_KEY`.
- **CLI flags** (https://code.claude.com/docs/en/cli-reference): `--permission-mode` accepts `default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions` (`manual` alias); `--dangerously-skip-permissions` is "equivalent to `--permission-mode bypassPermissions`" (neither is used); `--allowedTools` uses permission rule syntax; `--effort` levels `low`, `medium`, `high`, `xhigh`, `max`, `ultracode`; `--model` takes an alias or a full name; `--mcp-config` loads servers from JSON files or strings and with `-p` waits for pending servers up to `MCP_TIMEOUT`; `--session-id` must be a UUID; `--resume`/`-r` by ID, name or transcript path; `--output-format` `text`/`json`/`stream-json`; `--verbose` shows full turn-by-turn output.
- **Claude Desktop's approval** (https://modelcontextprotocol.io/docs/develop/connect-local-servers, "How Approval Works"): "Before executing any file system operation, Claude will request your approval"; "Each server exposes tools that Claude can use to perform actions, with your approval." I found no Anthropic page on the "always allow" choice; third-party help pages and user bug reports describe an "Allow always" option per tool (e.g. https://www.rememberthemilk.com/help/answer/mcp-troubleshooting-permissiondenied). The README says Claude Desktop asks before each tool call and that "always allow" stops it asking, which is what those sources describe, not something I could check in Claude Desktop here.

## 2. The lock, and what survives a restart

- `docs\cds_phase.lock`, created with `wx` before the runner starts (`phase`, `requested`, then the runner adds `runner_pid`, `started`); removed by the runner when Claude Code exits, by Stop, or as stale.
- "Alive" means: the pid exists **and** its WMI creation time is within 60 s of the recorded start **and** its command line is the runner's. So a pid reused after a reboot is not mistaken for the run, and Stop never kills it.
- Start also scans every `docs\*_run.json` for a live run, so a phase started by `run-phase.ps1` blocks the tools too (seen: P7).
- Everything Status/Reply/Stop need is in `docs\<phase>_run.json`; nothing lives in the server's memory. In the real run each call was a new workbench process.
